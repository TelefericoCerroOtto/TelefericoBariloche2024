# Shared TODO Workflow

This document defines how project TODOs are captured, triaged, and promoted between **Notion** and **GitHub**.

## Language Rule
**All artifacts created in GitHub Issues and Notion items MUST be written in English. Only the interactive chat can be in Spanish.**

## Quick Path

1. Search in Notion if the work already exists.
2. If it exists, update or merge the item instead of duplicating it.
3. If the user explicitly requested backlog capture or triage and the work doesn't exist, create **one row** in the **Backlog unificado** database.
4. When the work is already clear and needs a formal artifact, define the correct `Canal formal`.
5. Formalize explicitly (agent or manual dispatch), attach the corresponding link, and only then move to `Formalizado`.

Repository agents should use the Notion MCP for backlog reads and writes when it is available. If it is unavailable, they must report the limitation and must not pretend that backlog state was verified or changed.

Any other homonymous or suffixed database, especially `Backlog unificado (1)`, is non-canonical and must not receive operational reads or writes.

It is used for:

- capturing ideas or bugs detected in conversations
- consolidating inherited TODOs
- doing triage
- avoiding duplicates
- deciding when something already deserves a formal issue

### After Formalization

The formal execution source depends on the `Canal formal`:

- `GitHub Issue` → issue + branch/PR/commit
- `Cambio operativo` → change executed outside the repo with evidence or associated link
- `Documento / ADR` → persisted document or decision
- `No requiere` → no additional formal artifact
- `Otro` → external artifact justified in notes

The Notion row is not deleted: it is kept as an index and lightweight context.

## Standard Notion Schema

Each item is represented as **one row** with these properties:

| Property | Usage | Rule |
| --- | --- | --- |
| `Tarea` | short and actionable title | one single unit of work |
| `Estado` | operational status | use only allowed values |
| `Tipo` | classification | `Bug`, `Feature`, `Refactor`, `Content`, `Infra`, `Docs`, `Security` |
| `Área` | affected surface | one or more relevant areas |
| `Prioridad` | relative urgency | `P1`, `P2`, `P3` |
| `Fuente` | item origin | `legacy-notion`, `TODO.md`, `chat`, `meeting` |
| `Contexto` | path, domain, or section | example: `/faqs`, `teleferico-cms/auth`, `repo` |
| `Work ID` | stable backlog identifier | auto-generated by Notion, for example `TB-066` |
| `Branch` | one active or representative branch associated with the work | optional metadata, filled when useful |
| `Canal formal` | type of formal artifact expected | `GitHub Issue`, `Cambio operativo`, `Documento / ADR`, `No requiere`, `Otro` |
| `Enlace formal` | URL of the formal artifact | empty until the artifact exists |
| `Notas` | subtasks, acceptance, doubts, merge notes | brief text, do not turn the row into a giant mini-specification |

## Branch Convention Derived from Backlog

- `Work ID` is the stable work identifier. It doesn't change even if the branch changes.
- `Branch` stores one concrete active or representative branch, if useful. It does not replace `Work ID` as the stable identity.
- Record additional fresh follow-up branches in `Notas`.
- Implementation branches use one required convention:

```text
<type>/<dir>-tb-<digits>-<slug>
<type>/<dir>-no-backlog-<slug>
```

Examples:

- `fix/app-tb-066-login-refresh`
- `chore/root-tb-067-pause-legacy-vm`
- `feat/cms-tb-068-page-seo-fields`

Rules:

- `type` follows Conventional Commits (`feat`, `fix`, `chore`, `refactor`, etc.)
- `dir` follows `docs/CONVENTIONS.md` (`app`, `cms`, `tools`, `root`, or compound if applicable)
- `tb-<digits>` must come from the `Work ID` field; no-backlog work must use the literal `no-backlog` marker
- `slug` must be short, descriptive, and in kebab-case
- governance resolves one canonical `Work ID` from the tracked branch form; `Branch` is metadata and never a fallback association
- a different or empty Notion `Branch` cannot veto a uniquely resolved `Work ID`
- The complete policy for association between backlog, branches, and implementation PRs lives in `docs/backlog-branch-pr-policy.md`.

## Allowed Statuses

| Estado | When to Use It |
| --- | --- |
| `Inbox` | quick capture without minimal triage |
| `Clarificar` | lacks context, decision, scope, or validation |
| `Listo para formalizar` | already clear and needs some formal artifact |
| `Formalizado` | formal artifact already exists and the row has its link |
| `En progreso` | actively being executed |
| `Bloqueado` | there is an external or technical impediment |
| `Hecho` | truly resolved |
| `No hacer` | consciously discarded |

## Capture and Deduplication Rules

- Do not create almost identical rows with different wording.
- Search first by keywords, area, and context.
- If the new request is the same work with more detail, **enrich the existing row**.
- If the new request is a minor variant or subtask, add it in `Notas` unless it needs independent tracking.
- If two rows compete for the same outcome, keep one and mark the other as merged in `Notas` before moving it to `No hacer` or leaving it as a reference.

## Criterion for Choosing the Formal Channel

### `GitHub Issue`

Use it when:

- the work needs formal engineering tracking
- probably involves code, review, PR, or deploy
- it's convenient to preserve it as a stable execution artifact

### `Cambio operativo`

Use it when:

- the main work occurs outside the repository
- the change lives in GCP, Notion, IAM, console, DNS, Cloud Run, Cloud SQL, or another operational platform
- traceability is needed, but not necessarily a code issue

### `Documento / ADR`

Use it when:

- an explicit definition or decision is needed first
- the expected output is an agreed policy, design, or architecture
- that document may later derive into one or more issues or operational changes

### `No requiere`

Use it when:

- the task is so small or local that it doesn't warrant an additional formal artifact
- it's enough to resolve it and leave minimal traceability in Notion

## Criterion for Moving from Notion to GitHub Issue

Promote to GitHub when **most** of these conditions are met:

- the problem or change is already understood
- there is a minimal scope definition
- the work needs formal engineering tracking
- probably involves code, review, PR, or deploy
- it's convenient to preserve it as a stable artifact outside of a conversation

Do not promote yet when:

- it's still a vague idea
- it still needs confirmation if it's a real bug, decision, or valid request
- the request is better absorbed within another existing item

## Issue Promotion Protocol

1. Confirm that the row is in `Listo para formalizar`.
2. Confirm that `Canal formal = GitHub Issue`.
3. Create the GitHub Issue using the canonical contract from `docs/issue-context-contract.md`.
4. Paste the issue URL in `Enlace formal`.
5. Change the `Estado` to `Formalizado`.
6. If the issue groups several previous notes, summarize that merge in `Notas`.

### Explicit Execution (No Cron)

Formalization to issue is **on-demand** and done through human/agent flow (not by GitHub Actions):

- via agent
- or by a person operating the formal issue creation

There is no automatic promotion from Notion to GitHub.

### Minimum Required Issue Structure

Every issue promoted from Notion must respect the same backbone:

- `## Summary`
- `## Problem`
- `## Desired Outcome`
- `## Scope`
- `## Context`
- `## Repo Surfaces to Inspect`
- `## Acceptance Signals`
- `## Related Artifacts`

In `## Related Artifacts` always include:

- `Work ID`
- Notion URL of the source row
- related issues when they exist
- related PRs when they exist (or `N/A`)

If information is missing, use explicit placeholders (`TBD`, `Unknown`, `N/A`) and do not delete required sections.

## Protocol for Other Formal Channels

1. Confirm that the row is in `Listo para formalizar`.
2. Choose the correct `Canal formal`.
3. Create or execute the corresponding artifact.
4. Paste the reference in `Enlace formal` if applicable.
5. Change the `Estado` to `Formalizado` when the artifact already exists.

## Rules for Agents

When an agent receives an instruction like "add a TODO", "triage this backlog item", or "move this to issue", it must:

1. review the Notion backlog before creating anything
2. detect possible duplicates
3. decide whether to create, update, merge, or leave for clarification
4. respect the statuses and properties in this document
5. not write new items in `TODO.md` or legacy checklists
6. not assume that every clear task ends in a GitHub Issue; first choose the correct `Canal formal`
7. if a branch is created or suggested, use `<type>/<dir>-tb-<digits>-<slug>` for tracked work or the explicit `<type>/<dir>-no-backlog-<slug>` form for deliberately untracked work, then record one active or representative branch in `Branch` when useful
8. not trigger formalization by implicit cron: promotion to formal artifact is decided and executed explicitly

For concrete proposals, implementation requests, follow-ups, and regressions, run the intent and Git preflight in `docs/change-intake-preflight.md` before implementation edits.

## Legacy

- The old `TODO.md` in the repo has been archived and migrated to Notion.
- The old Notion `TO DO` page remains as an entry point and reference to the new backlog.
- The previous content has been preserved in a legacy file within Notion and in Git history.
