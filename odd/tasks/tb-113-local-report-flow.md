# TB-113 Local Report Flow

## Objective and boundary

Run the existing Next app, persistent Strapi CMS, and actual report worker locally. A small local queue substitutes only the Cloud Tasks operations the app uses. Survey data lives in Strapi; the same worker/CMS business API and the normal dashboard generate and display the report. The approved paid Google model may be called from local development after separate destination/credential authorization; staging remains the first real Cloud Tasks/Cloud Run integration.

This continues TB-113/#227 directly from commit `1e8ae39b1113e86748526106394e9356499c0ff3` on the user-authorized local child branch `feat/app-cms-root-tb-113-local-report-flow`. Draft PR #393 is not modified. Work stays uncommitted and unpushed until explicitly requested.

## L4 role-to-capability policy

- The approved 2026-09-02 policy in Engram observations #8019 and #8020 assigns the complete feedback bundle to Users & Permissions `Administrator` and `Digital Experience Operator`; it does not grant Strapi Admin Panel `Super Admin` access.
- The server-side Auth.js callback maps those exact role names to `feedback.read`, `feedback.comments.read`, `feedback.reports.read`, and `feedback.reports.generate`. Download is guarded by `feedback.reports.read`, matching the documented four-capability contract.
- On each session verification, the app re-reads the current user role and blocked state from Strapi; it recomputes capabilities from that result and denies blocked/missing users. Browser-supplied capability claims are ignored.
- CMS core generation/dispatch actions and app/worker custom Content API tokens remain separate permission gates. The implementation provisions no persistent role, permission, or token grant; the isolated harness creates only marker-owned fixtures and drops its unique database.
